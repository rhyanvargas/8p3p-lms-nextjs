# Better Auth Migration – Design

## 1. Architecture Overview

We are replacing AWS Amplify-based auth with **Better Auth + Postgres/Drizzle** while keeping the Next.js 15 architecture:

- **Server-first** with React Server Components (RSC) where possible.
- **Middleware** for optimistic route protection.
- **Client-side auth client** only for interactive flows (login, logout, reset, etc.).

### 1.1 High-Level Flow

1. User interacts with auth pages (login, sign-up, etc.).
2. Client uses `authClient` (Better Auth React client) to call `/api/auth/*` endpoints.
3. Better Auth server instance (`auth`) handles auth logic and persistence in Postgres (via Drizzle adapter).
4. On subsequent requests:
   - Middleware checks for a valid Better Auth session cookie (optimistic check) and redirects when needed.
   - Server components call `auth.api.getSession` to validate and load the session.

## 2. Components & Files

### 2.1 Better Auth Server Instance (`src/lib/auth.ts`)

Responsibilities:

- Configure Better Auth with:
  - `database: drizzleAdapter(db, { provider: "pg" })`
  - `emailAndPassword: { enabled: true }`
  - Email sending configuration (for verification + password reset).
  - Optional cookie configuration (name, prefix) if we need to align with existing conventions.

Key design choices:

- The `auth` export is the **single source of truth** for auth on the server.
- All server-side auth operations go through `auth.api.*` methods.

### 2.2 Drizzle + Postgres Integration

We will use the existing Drizzle `db` instance if available; otherwise, we introduce:

- `src/lib/db.ts`
  - Exports a Postgres connection pool (e.g., using `pg` or similar).
  - Exports the Drizzle `db` instance bound to that pool.
- Drizzle migrations include the Better Auth schema (generated via CLI).

Better Auth schema:

- Generated by `npx @better-auth/cli generate`.
- Applied via Drizzle migrations, versioned and tracked alongside the rest of the schema.

### 2.3 API Route – `app/api/auth/[...all]/route.ts`

Responsibilities:

- Expose Better Auth HTTP endpoints under `/api/auth/*`.
- Adapt the `auth.handler` to Next.js via `toNextJsHandler`.

Design:

- Minimal file that does not contain business logic; it simply mounts the handler.
- Changing the path (if ever needed) is done via Better Auth config + this route.

### 2.4 Client Auth Helper – `src/lib/auth-client.ts`

Responsibilities:

- Provide a typed client for the frontend to call Better Auth endpoints.
- Manage reactive auth state using Better Auth’s nanostore-powered client.

Design:

- Uses `createAuthClient` from `better-auth/react`.
- Configuration may include:
  - Base URL for `/api/auth` routes (default is fine in most cases).
  - Custom fetch configuration if needed.

Usage patterns:

- Login page: `authClient.signIn` (or equivalent) with email/password.
- Sign-up page: `authClient.signUp` with email/password.
- Navbar logout button: `authClient.signOut`.
- Password reset pages: `authClient` methods for initiating and completing reset.

### 2.5 Auth Pages

New or updated routes (client components):

- `app/login/page.tsx` (or `app/sign-in/page.tsx`)
- `app/sign-up/page.tsx`
- `app/forgot-password/page.tsx`
- `app/reset-password/page.tsx`
- `app/verify-email/page.tsx` (or a similar callback route)

Design guidelines:

- Use shadcn/ui components (Button, Input, Form, Alert) for consistency.
- Client components that call `authClient` for actions.
- Show clear success/error states.
- Avoid leaking sensitive details (e.g., whether an email exists).

### 2.6 Middleware – `middleware.ts`

Responsibilities:

- Provide fast, optimistic checks for session presence on:
  - `/dashboard`
  - `/courses`
- Avoid DB or heavy server calls in middleware.

Design:

- Use `getSessionCookie` or `getCookieCache` from `better-auth/cookies`.
- Keep existing route lists:
  - `protectedRoutes = ["/dashboard", "/courses"]`
  - `authRoutes = ["/login"]`
- Behavior:
  - No session cookie → redirect to `/login` for protected routes.
  - Session cookie present → redirect from `/login` to `/dashboard`.
- Any advanced validation (e.g., verifying session validity) is done inside server components using `auth.api.getSession`.

### 2.7 Server Components & Protected Pages

Example: `app/dashboard/page.tsx` becomes a server component that:

- Calls `auth.api.getSession({ headers: await headers() })`.
- If no session → `redirect("/login")`.
- If session → renders dashboard content using `session.user`.

This pattern ensures:

- Strong, server-side validation.
- No reliance on client-only checks for protected content.

### 2.8 Navbar Integration – `src/components/ui/navbar.tsx`

Responsibilities:

- Reflect auth state in the navigation (e.g., Login vs Dashboard/Logout buttons).
- Trigger logout via Better Auth.

Design:

- Remove Amplify hooks (`useAuthenticator`) and `signOut` imports.
- Use `authClient` (and/or its state store) to infer:
  - Whether a user is logged in.
  - Basic user info (e.g., email) if needed.
- Keep existing structure and styling; only swap auth wiring.

## 3. Email Delivery

Better Auth supports email flows for verification and password reset. We must configure:

- Email provider (e.g. SES, SendGrid, or another SMTP-compatible service).
- Environment variables for provider credentials and from-address.

Design goals:

- Encapsulate email configuration inside `auth.ts` or a dedicated email helper that Better Auth uses.
- Ensure failure to send email is surfaced via logs and user-facing messages.

## 4. Migration from Amplify – Design Considerations

### 4.1 Coexistence Phase

During early phases:

- Amplify remains present but unused by new flows.
- Better Auth is responsible for all new sign-up, sign-in, and password reset flows.
- Middleware and protected pages use Better Auth exclusively once switched.

### 4.2 Decommissioning Phase

Once Better Auth is fully in place:

- Remove all Amplify configuration files and imports.
- Remove Amplify-specific components and wrappers.
- Delete `amplify/` backend directory and `amplify_outputs.json`.
- Clean up AWS resources:
  - Cognito User Pool and Identity Pool
  - Amplify backend environments
  - Any auth-related Lambdas, DynamoDB tables, S3 buckets created solely for Amplify auth.

## 5. Security Considerations

- Use secure, HttpOnly cookies managed by Better Auth.
- Avoid storing sensitive data in local storage.
- Use generic error messages for auth failures to prevent enumeration.
- Rate-limit auth endpoints via Better Auth configuration or upstream measures.
- Ensure env vars and secrets are never logged.

## 6. Failure Modes & Handling

- **Misconfigured env vars**
  - `auth.ts` should fail fast with clear startup errors.
- **Database unreachable**
  - Auth endpoints should return a generic error and log root cause.
- **Email provider failure**
  - User sees a generic failure message; we log the underlying error.
- **Stale session cookies**
  - Middleware may treat them as valid (optimistic), but server components will detect invalid sessions and redirect to `/login`.

## 7. Observability

- Log auth-related errors at an appropriate level (e.g., warn/error) with minimal sensitive data.
- Optionally instrument metrics:
  - Failed login attempts
  - Reset requests
  - Verification link failures

## 8. Configuration & Feature Flags

- Env vars:
  - `BETTER_AUTH_SECRET`
  - `BETTER_AUTH_URL`
  - Database connection vars (Postgres)
  - Email provider vars
- Optional feature flags for future extensions (e.g., enable social login) can be added later around Better Auth configuration.
